## 处理流程与技术分工

消息接入 → 统一数据与去重 → 匹配用户配置的角色 → 模型提取分类/事项 → 校验和人工纠正 → 业务数据库 → 提醒调度与界面。

模型输入保留完整原文及来源、发送时间、时区等背景，不要求人工预先拆分语义。多事项拆分通常发生在模型提取结果中，用于程序分别保存、展示、安排提醒和处理完成/取消；原文与附件线索始终保留并可回溯。

- Python：处理消息、文件和规则；独立虚拟环境隔离依赖。
- JSON / Pydantic：定义统一字段、校验结构。通过类型校验不代表内容事实正确，仍需原文证据和纠正入口。
- 模型：理解语言，给出类别、摘要及事项候选；不负责猜测用户指定的重点角色，也不独自承担定时提醒。
- LangGraph：组织模型处理、校验、重试与人工确认节点；不同步骤之间有明确状态。
- FastAPI：提供导入、配置、查询与任务处理接口；工具包已有服务基础。
- SQLite：第一版本地业务数据，包括联系人、消息、文件、事项和提醒状态；后续可迁移 PostgreSQL。
- 调度与通知：模块四已实现独立于模型计时的后台循环、SQLite版本化outbox、租约和退避，支持终端与Windows本地通道；全量测试、实际通道提交及服务重启补发已验，用户已反馈桌面弹窗，同时报告历史邮件误提醒。
- Streamlit：沿用工具包界面技术，已交付独立HTTP客户端，展示消息列表、筛选、时间地点、研究问答、提醒与会话；原上游完整界面仍未运行。

上游 SQLite checkpoint 用来保存 Agent 执行状态；其 SQLite 模式的长期 store 当前实际在内存中，不能代替业务数据库。

## 数据与行为约束

- 消息保留来源、账号、来源 ID、发送/接收时间、时区、原文与完整性等级；完整内容、通知摘要和人工输入分别标识。
- 重点角色通过用户确认的来源身份匹配。相同昵称不自动视为同一人，跨平台关联可人工确认。
- 文件记录名称、类型、来源与可用状态；分别标识仅有通知、已取得文件、已提取文本、解析失败。分类同时显示依据来自消息还是文件内容。
- 同一条消息可产生多个事项。每个事项分别保存截止、起止、地点、证据片段和确认状态。
- 相对时间以原消息发送时间为基准，按业务规定的北京时间解释。用户已确定裸“周三/周四”按原消息所在自然周（周一至周日）定位，即使已过去也不自动跳下周；“周三前”日期沿用该规则，未配置钟点时不补 23:59，也不重复询问属于哪周。日期与周/月/年范围可保留各自精度，缺钟点不等于日期无法确定。详见[时间解释规则](TIME_POLICY.md)；第十课归一化接口保持原有限范围，第十一课另增解释入口。
- 时间类型初拟使用橙色截止、蓝色时段、紫色地点；同时提供文字标签。逾期、已完成、已取消分别标识；颜色与提醒时机可调整。
- 提醒策略由用户配置；需支持重复输入去重、修改或取消后的提醒更新、完成后停止提醒。
- 已确认Windows桌面通知＋列表；自动规则默认关闭，日期级事项只在用户配置提醒钟点后计划，不修改原时间精度。`submitted`仅表示交给通道，不表示已读或跨OS恰好一次；旧tasks目前只有pending/completed，取消提醒不等于取消任务。
- 消息中出现的命令只是待处理内容，不能因此执行附件或修改用户配置。原始内容的模型传输范围在接真实数据前确定。
